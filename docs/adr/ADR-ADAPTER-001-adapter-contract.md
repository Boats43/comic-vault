# ADR-ADAPTER-001 — Adapter Contract, GK-147 Expansion Gate, Listing-as-Projection

**Status:** Ratified (Master Architecture Summit, Phase 1). **Rulings covered: 30–34, 37.**

## Context

CLAUDE.md's own AssetCore architecture already states the intended shape: "AssetCore is now universal — operates on primitives only... All format-specific domain knowledge lives in adapters." `src/adapters/ComicAdapter.js` (312 lines, 4/4 functions) is the one adapter that exists; `BookAdapter.js`/`CardAdapter.js` are documented roadmap (Session 4A/4B), not built. GK-147 (`docs/DATA-1-READINESS.md` D2, found during the DATA-1 readiness interrogation) proved the "universal" claim is not yet true in practice: `decisionEngine.js:137-151` hard-gates identity-completeness on comic-specific `issue`/`publisher` presence; `pricingEngine.js:126` carries its own TODO admitting a comic-specific assumption; `pricingEngine.js:111` hardcodes the 1956 Silver Age boundary inside a module claiming to be domain-agnostic; `pricingEngine.js:46,183` exposes `isMegaKey` as if it were universal. GK-147's own registry text was explicit about its purpose: "this ticket is the fence, not a repair" — logged so a second adapter isn't built on top of an assumption nobody checked. Separately, GK-150's Asset Network census finding (`bundleId = ebayItemId`) showed a second, related defect class: a GrailKey concept (a bundle) deriving its own identity from an external marketplace's ID scheme, with no independent existence of its own.

## Decision

**Ruling 30 — the adapter contract is formalized, not just documented as intent.** An adapter implements a fixed, small interface (matching `ComicAdapter.js`'s own existing 4-function shape: `detectKeyValue`, `verifyStory`, `computeEraRisk`, `sanitizeFormatTitle`, or their equivalents for a new asset class) and NOTHING outside that interface may be format-specific. AssetCore (`identityCore.js`, `pricingEngine.js`, `decisionEngine.js`) may only call INTO the adapter interface for anything format-specific — it may never itself branch on asset type, hardcode a format-specific threshold, or assume a format-specific field exists.

**Ruling 31 — GK-147 is the literal exit gate for building a second adapter.** No `BookAdapter.js`/`CardAdapter.js` (or any future adapter) may be started until every item GK-147 named is either fixed (moved behind the adapter interface) or explicitly re-scoped with its own ticket and rationale for why it can wait. This is stated as a hard sequencing rule, not a preference: building a second adapter on top of an AssetCore that secretly assumes comic-shaped data would silently reproduce the exact "second, competing truth system" failure class this project's other ADRs and `THE REBUILD RULE` already exist to prevent, one layer up — a hypothetical `BookAdapter.js` would either inherit the comic-specific bugs unknowingly, or need its own parallel patches, defeating the point of AssetCore's universality claim.

**Ruling 32 — listing-as-projection.** A marketplace listing (eBay, Whatnot, any future channel) is a PROJECTION of the canonical `gkAssetId`/identity/pricing data, never an independent source of truth and never the origin of a GrailKey-owned identifier. GK-150's `bundleId = ebayItemId` is the concrete defect this ruling fixes: a bundle's real identity is a GrailKey-owned grouping of `gkAssetId`s (ADR-ASSET-001); `ebayItemId` becomes an `external_map` row (ADR-ID-001's own external-reference model) — one mapped reference among possibly several external channels, never the primary key. This generalizes past bundles to every listing-shaped concept the adapter/commerce layer produces.

**Ruling 33 — commerce separation.** Identity/catalog concerns (what is this, which physical copy, who owns it) are architecturally separate from commerce concerns (is it listed, at what price, on which channel, in what state of a sale). The commerce layer CONSUMES identity/catalog/pricing data through defined interfaces; it never becomes a second place identity or ownership facts get written. This is the same principle ADR-AUTH-001's four-step authorization chain already assumes (asset authorization is checked before marketplace-account authorization, not folded together) — stated here as a structural separation, not just an authorization-order rule.

**Ruling 34 — commerce-layer idempotency.** Listing creation, delisting, and bundle operations are idempotent under the same discipline ADR-API-001 (Ruling 26) and ADR-ID-001 (mint idempotency) already require elsewhere: retrying a "list this asset" request must never produce two live listings for the same `gkAssetId` on the same channel.

**Ruling 37 — the adapter interface itself is versioned and stable independently of any single adapter's implementation.** Changing what AssetCore expects from an adapter (adding a required function, changing a signature) is an interface-version change, reviewed with the same weight as a schema migration — an adapter written against interface v1 must not silently break when AssetCore evolves, matching ADR-API-001's own versioning discipline extended to this internal contract.

## Invariants

1. No file under `src/lib/` (AssetCore) branches on asset type, format, or any format-specific field name.
2. No second adapter is started while any GK-147 item remains unresolved and unre-scoped.
3. No marketplace/channel identifier (eBay item ID, Whatnot listing ID, etc.) is ever used as, or stored as, a GrailKey primary key — always `external_map`.
4. Listing/bundle mutations are idempotent per Ruling 34.
5. **A category adapter is optional at the physical-asset-kernel level.** A `gk_asset` may be minted, owned, carry media, and participate in kernel economics (acquisition, valuation, inventory, outcomes) with NO category adapter attached at all. In that state: automated identity/condition/valuation are `UNKNOWN` (a legal, first-class value, not an error or a placeholder); operator-supplied facts remain fully valid; the durable kernel remains fully usable. This is a first-class statement of THIS interface contract, not merely reasoning contained in Amendment A3's Ruling 40 — added here (U3 Reconciliation, Amendment A4) because the base contract, before this addition, never stated adapter-optionality as part of the interface itself, only as later amendment prose. `docs/ASSETCORE_INTERFACE.md` (the separate, narrower AssetCore pricing/decision contract) does not need an equivalent clause — an adapter-absent asset never calls into AssetCore's pricing/decision engine at all (no automated valuation, per U1/U4's own scope), so that interface is simply never invoked, not invoked-with-an-optional-adapter.

## Consequences

- GK-147 gains real teeth: it is not just a documented debt, it is a hard blocker on the Session 4A/4B roadmap CLAUDE.md already describes.
- GK-150's fix has a concrete target (`external_map` + `gkBundleId`, per that ticket's own registry text) and is no longer just "logged, no fix" — this ADR is its remediation path (amendment A2: "GK-150 OPEN/remediation-ADAPTER").
- Future adapters (Book, Card) inherit a real, enforced contract rather than needing to independently discover which parts of AssetCore actually are universal versus quietly comic-shaped.

## Rejected Alternatives

- **Fix GK-147's specific 4 named items and consider the adapter boundary "good enough."** Rejected: GK-147's own text frames itself as "the fence, not a repair" — a spot-fix of the 4 known instances doesn't establish the STRUCTURAL guarantee (Invariant 1) that a fifth, not-yet-found instance can't exist; the contract must be enforced, not just patched around known cases.
- **Let `BookAdapter.js` work proceed in parallel with GK-147 remediation.** Rejected: risks the second-adapter effort discovering AND working around the same comic-specific leakage independently, duplicating the fix and likely diverging from it — sequencing (Ruling 31) is cheaper than parallel rediscovery.
- **Keep `ebayItemId` as a bundle's primary key for simplicity (it already works for the single-channel prototype).** Rejected: GK-150's own finding already identifies why — no independent existence for non-eBay bundles (Whatnot, local sale, any future channel), and the "external ID as primary key" pattern is exactly the shape ADR-ID-001's `external_map` model exists to replace project-wide.

## Implementation Gates

- `BookAdapter.js`/`CardAdapter.js` (Session 4A/4B, CLAUDE.md roadmap) are blocked until GK-147 is closed or explicitly re-scoped per Ruling 31.
- Any new marketplace/channel integration must route its own identifiers through `external_map` from its first commit, never introduce a new "external ID as primary key" pattern.

## Related Tickets

- GK-147 — OPEN/exit-gate-ADAPTER (per amendment A2) — the founding finding and the literal gate this ADR enforces.
- GK-150 — OPEN/remediation-ADAPTER (per amendment A2) — fixed by Ruling 32 (listing-as-projection), implementation not yet built.

**Ruling 45 — U4 entry contract, re-derived from a durable-recovery PROPERTY rather than asserted as a fixed step order; supersedes this ruling's own prior "asset → media → projection → link" language, which is not carried forward.** Today's only live capture caller (`GrailKeyOperatorPanel.jsx`'s `captureAsOwnedAsset`) starts from an ALREADY-EXISTING `collection_item` row and mints `gk_asset` second. U4 needs the reverse (no pre-existing `collection_item` at all). No schema change required for any of what follows — every mechanism cited is already committed code, re-verified directly this pass.

**Idempotent mint — GK-163 already covers the capture-mint path; no new mechanism required.** `docs/TICKET-REGISTRY.md`'s real GK-163 entry (`CLOSED`, 2026-08-23) names `createPhysicalAsset` explicitly as one of the 10 Asset Service operations under its class-wide request-fingerprint law: same `idempotencyKey` + same semantic payload (`{captureBasis, assetClass, source}`) replays the original result verbatim, zero new rows; a different payload under the same key throws `IdempotencyConflictError`, never a silent second mint. Re-confirmed directly in `src/modules/assets/service.js:94-111` (`createPhysicalAsset`'s own `computeRequestFingerprint`/`checkIdempotencyReplay` call). A SECOND, independent layer backs this further: `repo.mintAsset` is built on `entity_mint_basis`'s own `UNIQUE (basis_namespace, basis_key)` constraint (migration `0003`) — even a caller that varies its `idempotencyKey` but resolves to the same capture basis (same principal + same correlationId/session) gets `outcome:'resolved-existing'`, never a second physical identity. **`attachMedia` is independently covered by the same law** (`{gkAssetId, captureRole, sha256}` fingerprint) — a duplicate photo-attach replays too. **Generic Asset Mode reuses this mechanism as-is; no new idempotency design is needed for the mint or media-attach steps.**

**Durable-pointer-at-every-step — the governing property, and the order it requires.** Required property: after every successful step of generic capture, the server holds enough durable state to complete or recover the capture WITHOUT the originating device. Verified directly against schema/code, not asserted: `collection_item_link` (`collection_item_id TEXT PRIMARY KEY, gk_asset_id UUID NOT NULL REFERENCES gk_asset(id), ...`) has a real, indexed (`collection_item_link_asset_idx`), enforced FK to `gk_asset` and NO FK to `collection_item` — it is genuinely, independently queryable the instant it exists, by either its `collection_item_id` (`getCollectionItemLink`, `src/modules/assets/repository.js:505-508`) or its `gk_asset_id` (the index), with zero dependency on any `collection_item` row ever having existed. `linkCollectionItem` (`src/modules/assets/service.js`) confirmed to check only for a pre-existing *link*, never for a pre-existing `collection_item` row, before inserting.

This means a link row, once created, IS itself a durable recovery handle — it carries both the stable `collection_item_id` the still-pending projection must use and the real `gkAssetId` it belongs to, discoverable from any device via a targeted, indexed query. The reverse is not true: a `gk_asset` with no link at all is discoverable only via a principal-wide anti-join (Case A below) — an irreducible window, since `collection_item_link.gk_asset_id` is `NOT NULL`, so no link can exist before an asset does. **Ratified order: `gk_asset` (mint) → `media` (attach) → `collection_item_link` (link) → `collection_item` (projection).** Media is sequenced before the link, not after, on the same property: the physical evidence (photos) is the irreplaceable fact this whole flow exists to secure durably; the link and projection are reconstructible administrative pointers that can be recreated at any time once asset+media exist, so they are ratified as the last two steps, with the link (a real, targeted, FK-backed recovery handle) placed strictly before the projection (a caller-supplied id with no recovery handle of its own beyond the link that will point to it).

**Record semantics, ratified — and explicitly restated per this dispatch's own instruction:** `collection_item != gkAssetId`. `gk_asset` = durable physical truth (identity, ownership, media, economics) — a catalogue record is never physical identity, and nothing above changes that. `collection_item` = the recoverable, user-facing Collection-tab projection — what the operator browses, never itself physical identity. `collection_item_link` = the durable edge between projection identity and physical identity, deliberately decoupled from `collection_item`'s own existence so it can serve as a recovery handle when the projection is the piece still missing. **The exact creation order above is subordinate to this recovery property, not the reverse** — the order was re-derived FROM the property (by checking which table is independently, durably queryable at each point), not chosen first and justified after.

**Ruling 46 — server-side orphan/incomplete-capture detection, designed here, not built.** Local retry-on-reconnect (the existing `collectionSync.js`/`retryPendingBuyerDecisions` pattern) improves UX but is explicitly NOT sufficient as the sole recovery mechanism — recovery must work after logout/login, from a different device, with no dependence on the original device's local IndexedDB. Two server-side checks, both real anti-joins scoped to one principal (bounded, indexed, not unstructured full-table scans), for a future dispatch to build:

- **Case A — physical orphan:** a `gk_asset` the principal owns with zero `collection_item_link` rows pointing at it. Query shape: `gk_asset` (scoped via `current_owner.owner_principal_id = $principalId`) `LEFT JOIN collection_item_link ON collection_item_link.gk_asset_id = gk_asset.id WHERE collection_item_link.gk_asset_id IS NULL` — an anti-join over the real, indexed FK, never a scan of every asset in the system. Recovery action: mint a fresh `collection_item_id` and complete the link + projection steps the original capture never reached.
- **Case B — projection missing:** a `collection_item_link` row exists (`linked_by_principal_id = $principalId`) whose `collection_item_id` has no matching `collection_item` row (`(principal_id, id)`). Query shape: `collection_item_link LEFT JOIN collection_item ON collection_item.id = collection_item_link.collection_item_id AND collection_item.principal_id = $principalId WHERE collection_item.id IS NULL` — recovery action: re-run the exact `collection_item` creation call using the `collection_item_id` ALREADY recorded on the link row (no new id is invented, preventing the same asset from ever acquiring two different catalogue ids).

Both checks are designed to run server-side, triggerable at login/reconnect from any device — a future dispatch's own scope, not built here.

**U4 acceptance addition — duplicate-submit proof, required.** Beyond the existing single-capture acceptance sequence: trigger the capture action twice (or retry with the identical capture `idempotencyKey`, matching `GrailKeyOperatorPanel.jsx`'s own existing `getOrCreateCaptureIdempotencyKey` convention). Required result, proven by GK-163's mechanism above, not a new build: exactly one `gkAssetId` exists for that physical capture; no duplicate `gk_asset`, no duplicate media row, no duplicate `collection_item_link`, no duplicate `collection_item` row — every operation in the chain replays its original result verbatim on the second submission.

**U4 zero-migration, reconfirmed.** Every element of this contract (`assetClass` param, `attachMedia`, `linkCollectionItem`, `collection_item`'s caller-supplied id, `listMyAssets`, the GK-163 idempotency law, both anti-join shapes above) already exists in committed code. No table, column, or constraint is missing.
