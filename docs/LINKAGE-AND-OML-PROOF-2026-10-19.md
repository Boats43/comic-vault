## Engineering invariants (recorded)
1. A recommendation does not confer execution authority. 2. A Collection row does not, by itself, prove ownership. 3. Physical-asset linkage requires evidence of a real owned object. 4. A test that reimplements its subject does not certify the real trust boundary. 5. Timing observations do not establish root cause without tracing the awaited operations.

## A1 — how `collection_item_link` (and a gkAssetId) come to exist
- **Only path:** `captureFromScan` (`src/modules/capture/service.js` ~l.275) → `linkCollectionItem` (`src/modules/assets/service.js:743`, insert at `:801` → `repository.js:584 insertCollectionItemLink`). `captureFromScan` is reached only via `api/capture-scan.js`.
- **Callers of `/api/capture-scan` in the frontend:** (a) `GrailKeyOperatorPanel.jsx` (~l.241) — the explicit **"Capture as Owned Physical Asset"** button (GK-218), carrying an `ownershipAttestation: 'operator-panel'`; (b) `src/lib/genericAssetCapture.js` — explicit SAVE AS GENERIC. Plus the operator-run relink tool (`scripts/gk270-*`), a reconciliation of existing links, not a creator of ownership.
- **Not** from: ordinary reference scanning, saving a catalogue result (`persistCollectionItem` → `/api/collection` only), bulk import, or any automatic flow. Ownership semantics: linkage = "the operator asserted, on a specific catalogue record, that they hold this physical copy, and supplied photo bytes of it".

## Task 3 — `collection-sync-closeout-live-proof` timeout: root cause
Traced with a diagnostic copy: the fake IndexedDB request **succeeds** (`put` applied, `req.onsuccess` fired) and `src/db.js` `runMutation` has assigned `transaction.oncomplete` — but the fake `transaction` object (`{objectStore}`) has no event machinery, so **`oncomplete` never fires** and the awaited promise never settles (GK-234 B1 deliberately resolves only on `oncomplete`, the real commit signal). No network/database call was pending; IndexedDB work completed; the test waited on an event that never fires. Product behaviour is correct per the IDB spec (a real transaction fires oncomplete) → **harness-only**. Minimal harness repair applied to the real test: the fake transaction fires `oncomplete` after its last request (and `onabort` on error). The first repaired run then exposed a second, independent stale assumption: a fixed identity ("Brave and the Bold #141 1978") reused across runs is correctly flagged by GK-279 (`copy-review`); fixed with a per-run unique title. Result **16/16 in 3 s** (was TIMEOUT at 240 s). The same fake-IDB defect is the suspected cause for `collection-image-sync` (not touched). It cannot be reproduced "outside the harness" because Node has no IndexedDB; real browsers fire `oncomplete`.
