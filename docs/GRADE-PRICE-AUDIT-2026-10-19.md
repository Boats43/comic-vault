## Task 1 — server linkage refusal (`api/list-ebay.js`)
`PHYSICAL_ASSET_NOT_LINKED` (409) is returned only when the caller is the authenticated owner of the named Collection row (`getMyCollectionItem` is principal-scoped) and `resolveCollectionItemLink` finds no link. A non-owner or a nonexistent row gets the generic `GRAILKEY_LINKAGE_INCOMPLETE` (byte-identical, no existence/linkage oracle). Distinct, machine-readable `reason` values keep the established code: `GK_ASSET_ID_MISSING`, `DECISION_EVENT_MISSING`, `OPERATOR_ACTION_MISSING`; the 403 for an unusable receipt now also carries `refusalReason` (`AUTHORITY_RECEIPT_UNVERIFIED_ABSENT`, `…_UNBOUND`, `…_ASSET_MISMATCH`, `…_EVIDENCE_VERSION_STALE`, `…_IDENTITY_MISMATCH`, or `AUTHORITY_INSUFFICIENT`). Nothing mints, links, attests, writes authority or calls eBay. The client now sends `collectionItemId` (a lookup key only).

## Task 2 — client affordance (`src/lib/physicalLinkStatus.js`, `src/App.jsx` CollectionDetail)
State comes from the existing authenticated `GET /api/assets?collectionItemId=`: 200 with `asset.asset.id` → LINKED; 404 → NOT_LINKED (the server answers 404 identically for no-link / not-yours / no-row; for the listing control all three mean "no executable link for this principal"); 401/no session → UNAUTHENTICATED; network/5xx → UNAVAILABLE (own label, never reported as "not linked").
